ESTUDO DE CASO / INTEGRAÇÃO DE DADOS

Do S3 ao OCI: entrega de dados por cliente

Como organizar a distribuição diária de arquivos Parquet de Data Quality entre nuvens, com destino variável, falhas visíveis e retomada por data.

Alexandre RobertoSetembro de 2026Amazon S3 · Azure Data Factory · Azure SQL · Azure Blob · OCI · Kubernetes

01 / CONTEXTO

O problema

Arquivos de Data Quality eram disponibilizados diariamente no Amazon S3, separados por cliente. Cada arquivo precisava chegar ao malote correspondente no OCI Object Storage. O destino dependia do código do cliente em uma base Azure SQL, portanto uma cópia com endereço fixo não resolveria o lote inteiro.

A execução usava a data de referência D-1. Também precisava distinguir ausência de cadastro, falhas de comunicação e etapas ainda pendentes, para que um problema de um cliente não bloqueasse as demais entregas.

02 / DESENHO

Arquitetura da entrega

ORIGEMAmazon S3Parquet · D-1
→
ORQUESTRAÇÃOAzure Data Factorycliente · lookup · cópia
→
STAGINGAzure Blobárea intermediária
→
DESTINOOCI Object Storagemalote do cliente

Azure SQL Database fornece o mapeamento código do cliente → malote OCI.

Kubernetes CronJob copia arquivos prontos do staging para um diretório compartilhado com o portal, em uma etapa posterior.

O diagrama mostra a sequência funcional. O mecanismo específico de transferência e autenticação entre Blob e OCI não está documentado no material deste caso.

03 / IMPLEMENTAÇÃO

Da descoberta à entrega

01

Descobrir a entrada

Um Schedule Trigger inicia a rotina diária. O pipeline calcula D-1 e consulta os arquivos disponíveis para esse ciclo. Descobrir o que chegou é uma etapa distinta de iniciar a agenda.

02

Resolver o destino

O ForEach percorre os clientes encontrados. Para cada código, um Lookup consulta o Azure SQL e obtém o malote cadastrado. A resposta é validada antes de movimentar os arquivos.

03

Mover e acompanhar

Os arquivos seguem do S3 para o Azure Blob Storage como staging e, depois, para o malote no OCI. Concluir a etapa no Blob não significa que a entrega no OCI terminou; cada etapa exige acompanhamento próprio.

04

Disponibilizar no portal

A cada 30 minutos, um CronJob do Kubernetes executa a rotina que copia arquivos prontos do staging para o sistema de arquivos compartilhado com o portal. A visualização pelo usuário ocorre depois da movimentação entre nuvens.

04 / OPERAÇÃO

Exceções e reprocessamento

Se um cliente não tinha malote cadastrado, a rotina registrava a ocorrência e seguia para os demais. Repetir a cópia não corrigiria uma decisão de roteamento ausente. Para falhas transitórias de comunicação, havia tentativas de nova execução, logs e alertas.

Após investigar e corrigir a causa, a equipe podia reprocessar uma data específica. A análise distinguia cinco perguntas: o arquivo chegou ao S3? O cliente tinha destino? A cópia no Blob terminou? O OCI recebeu o objeto? O portal recebeu o arquivo?

05 / RESULTADO

O que a solução entregou

A distribuição diária por cliente foi automatizada, com roteamento por cadastro, registro de exceções e caminho de retomada por data. A arquitetura separou a entrega no OCI da disponibilização no portal e tornou mais claro em qual etapa investigar uma falha.

Este relato descreve o funcionamento e o resultado operacional. Não há métricas de volume ou redução de tempo publicadas para este projeto.
